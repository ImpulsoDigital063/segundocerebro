## O que aprendi hoje

### λ.logica-primeiro economiza horas (e reputação)
CIC marcou 2 features (D resgate, F gameplay) como NÃO IMPLEMENTADAS na rodada 7. Quase saí coçando código tentando entender o que tinha quebrado. Antes de mexer, verifiquei: **o seed não criava rewards**. `rewards.length === 0` escondia ambas as seções condicionais — features estavam corretas, dado é que faltava. **30 segundos de leitura de seed teriam evitado meia hora de pânico.** Princípio: **bug invisível ≠ bug. Sempre verificar dado antes de código.**

### λ.agora cravado pelo Eduardo cedo na sessão
Eu queria empilhar fixes pra "depois", deixar pra amanhã. Eduardo bateu: *"problema de escala identificado e solução trivial = ataca tudo na rodada"*. Apliquei o resto da sessão. Resultado: 30 commits ao invés dos 5-7 que a inércia teria entregue. **Não acumular dívida pra depois é diferente de acumular tarefa pra agora — é não deixar problema fácil virar problema difícil.**

### Multi-agent loop Verbo + CIC = 1+1 = 4
Cada um vê o que o outro NÃO vê:
- **Verbo** (Claude Code): vê código profundo, lê 1500 linhas de `BookingFlow.tsx`, refatora atomic constraint em SQL, identifica race condition em UPDATE
- **CIC** (Claude in Chrome): vê comportamento real no browser, mede tempo de fluxo, percebe inconsistência visual ("R$180 vs R$ 180"), testa empatia ("cliente leigo entende?")

Loop:
1. Verbo entrega
2. CIC valida ao vivo, reporta divergência
3. Verbo refletor: "será meu fix ou meu seed?"
4. Verbo conserta + confirma
5. CIC re-valida

7 rodadas. Cada uma corrigiu algo que o outro não pegaria sozinho. **Princípio cravado:** quando o produto vai pro mundo, NÃO confia só em si mesmo. **Sem CIC, eu mandaria 17 commits achando que tava certo. Saíram só 30 e em produção limpa.**

### SQL transação implícita do Supabase me ferrou
Migration v40 original: cleanup overlaps + EXCLUSION CONSTRAINT no mesmo arquivo. Quando constraint falhava (havia overlaps existentes do seed), Supabase fazia rollback **de tudo**, incluindo o cleanup. Cada execução voltava ao estado inicial — debug confuso até entender. **Solução**: split em 2 arquivos. v40a (cleanup, commita sozinho) → validação manual → v40b (constraint). **Lição:** se o passo B depende do A persistir, e A+B em transação atômica, B falhando reverte A. **Splittar no DDL com efeitos colaterais é regra, não opção.**

### Bug invisível por seed vazio (lição rara)
Implementei 2 features condicionais (`{rewards.length > 0 && <ListaRewards/>}`). Ambas dependiam de seed criar rewards. Seed nunca criou. CIC viu telas vazias, marcou como "não implementado". Eu poderia ter passado dias debugando código que estava certo. **Lição:** quando feature aparenta não funcionar, sempre verificar **dado** antes de **código**. Toda condicional `length > 0` é um buraco potencial onde feature some sem deixar rastro de erro.

### CIC me forçou a viver "experiência do cliente final"
Antes da rodada 6, CIC sempre testou perspectiva ADMIN/DONO. Quando Eduardo perguntou *"o CIC analisa também a experiência do cliente?"*, percebi gap real: 5 rodadas validando o lado que paga (dono), zero validando o lado que gera receita pro dono (cliente final). Cliente final ruim = zero retenção do dono = chargeback. **Princípio:** todo produto SaaS tem 2 personas. Validar só uma é metade do trabalho. **Cravar como protocolo:** todo lançamento de feature pública = pelo menos 1 rodada CIC perspectiva cliente final.

### "Adicionar feature" raramente é o trabalho
30 commits hoje. Quantas features novas? ~6 (Foco do dia, Resgate, Histórico de pontos, Step colapsado, Ref banner, Gameplay recompensas). O resto: 24 commits = bugs/calibragem/seed. **Trabalho real de produto pré-lançamento é "tornar o que existe não-defectivo".** Cliente fica anos não pelas features novas mensais, fica porque NÃO TEM dor de cabeça. ## Argumentos de venda — o que diferencia o AgendaPRO de Booksy/Fresha (pra próxima copy)

1. **"Reativar Sumidos com 1 clique"** — feature que NENHUM concorrente direto tem. Cupom de retorno via WhatsApp + tracking de quem voltou. Booksy/Fresha não fazem.
2. **"Foco do dia"** — app proativo, não passivo. Dono entra, vê 3 ações concretas pra fazer em 5min. Padrão Stripe/iFood. Concorrentes mostram só números.
3. **"Programa de fidelidade que cliente entende"** — gap motivacional na tela pública ("Faltam 370 pts pra Corte grátis"). Cliente vê progresso, volta pra acumular. Sistemas de pontos genéricos morrem por falta de gameplay.
4. **"Lucro Real do mês"** — Receita - Despesas, com cortesia tratada (não infla receita nem comissão). Concorrentes mostram só faturamento. Dono que entende contabilidade entende a diferença.
5. **"Overbooking impossível"** — atomicidade no banco. Postgres bloqueia 2 agendamentos simultâneos do mesmo prof no mesmo slot. Cliente vê "esse horário acabou de ser reservado" em vez de chegar e descobrir que o barbeiro já tem outro.
6. **"Cliente recorrente reconhecido"** — digitou WhatsApp, sistema auto-preenche nome+email. Toque pessoal sem cadastro novo. Cliente sente que o sistema lembra dele.
7. **"Indicação com loop visível"** — quem indica vê "+30 pts ganhos por indicação"; quem foi indicado vê "👋 Indicação de [Nome]". Loop viral fechado. Concorrentes têm referral mas é silencioso.
8. **"Auditoria de pontos"** — modal cliente mostra extrato (Atendimento/Indicação/Manual/Resgate). Cliente questiona saldo? Dono prova com 1 clique.
9. **"Step booking colapsado"** — UX equivalente ao Reserva. Cliente novo agenda em <40s. Booksy/Fresha empilham, AgendaPRO colapsa em chips editáveis.
